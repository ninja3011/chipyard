## Honest scoping note before starting

The existing `RocketArty100TConfig` bitstream (clean timing, committed) has **no VGA peripheral at all** — that was explicitly flagged as a placeholder in every prior report (`ARTY-A7-100T-PROJECT-SCOPE.md` Tier 1b). Making DOOM *and* Bad Apple actually visible requires real new Chisel hardware (a framebuffer peripheral + VGA timing generator + pin binding), not just software. That's genuinely new RTL work, scoped previously as "its own focused session" — this session **is** that focused session, per explicit instruction tonight. Proceeding with real implementation, not a stub.

Given the size of this (new peripheral, new IOBinder/HarnessBinder, new pin constraints, software rewrite for two payloads, full elaborate→synth→place→route cycle with real hardware timing risk), I'm building the smallest *real, working* version first — monochrome framebuffer, matching what Bad Apple's pipeline already produces natively and what DOOM can be thresholded down to — rather than a full-color design that multiplies risk for no bring-up-day benefit.

## Plan

1. Design a minimal VGA output peripheral in Chisel:
   - Small on-chip framebuffer (`SyncReadMem`, sized for a low resolution monochrome image — cheap in BRAM, avoids needing a DMA engine off DRAM).
   - A TileLink-addressable write port so the CPU can update it like normal memory.
   - A free-running VGA timing generator (h-sync/v-sync/pixel-valid) clocked by dividing the existing 50MHz bus clock down to a real VGA-standard pixel rate, reading the same framebuffer on a second port for scanout.
   - Real Pmod VGA pin mapping, using the Arty's actual JA/JB pin-to-FPGA mapping already present in `arty-master.xdc` (not guessed) and Digilent's standard 12-pin Pmod VGA pinout.
2. Wire it into a **new** config (not modifying the already-clean, already-committed `RocketArty100TConfig`) so tonight's new hardware risk is isolated from the working baseline.
3. Elaborate first (fast, catches Chisel/FIRRTL errors early) before spending any Vivado time.
4. Update the bare-metal platform layer: `DG_DrawFrame` writes real framebuffer bytes at the peripheral's real, confirmed address (not the placeholder from before).
5. Add a bare-metal Bad Apple player, reusing the existing `.vidf` format and the same bare-metal syscall/newlib foundation already built for DOOM.
6. Run the real Vivado flow (synthesis → place → route → bitstream) via the same Windows bridge already set up. Follow the explicit loop: execute, if error diagnose and fix for real (chipyard docs first, no guessing), if clean move to the next step.
7. Report real, verified status — timing numbers, utilization, what's genuinely done vs. still open — not an optimistic summary.

## Progress log

- **Peripheral designed**: `chipyard.vga.TLVGAFramebuffer`, monochrome 320x240 framebuffer scanned out at 640x480 (2x pixel-doubling), 3-signal output (HSYNC/VSYNC/VIDEO) on Arty's JA header using real, already-defined pin mappings from `arty-master.xdc` (G13/B11/A11).
- **Real architecture bug caught before it compiled wrong**: initially planned to mix the trait into `fpga.arty100t` (board-specific package). Chipyard's dependency graph runs `fpga` depends on `generators/chipyard`, never the reverse -- `DigitalTop.scala` (in `generators/chipyard`) can't reference a type from `fpga`. Moved the peripheral to `generators/chipyard/src/main/scala/vga/`, matching exactly where `chipyard.example.GCD` (the reference pattern this was modeled on) already lives, for the same reason.
- **Real elaboration bugs found and fixed, one at a time, each confirmed by re-running elaboration rather than guessing the fix worked**:
  1. Ambiguous `LazyModule`/`InModuleBody` import (two overlapping diplomacy imports) -- fixed by dropping the redundant one, matching GCD's own working import set.
  2. `IOPin` not found -- it lives in `sifive.fpgashells.shell`, not `sifive.fpgashells.ip.xilinx` as assumed; added the correct import.
  3. `TLRegisterNode`+`regmap`'s automatic DTS "reg" resource binding failed hard (`must be a single range`) once the framebuffer had more than a couple of individually-mapped fields -- confirmed via a fast empirical test (a deliberately tiny 64x48 framebuffer hit the exact same failure), proving it wasn't a scale issue but a structural one: `regmap` is built for a handful of control registers, not a multi-KB bulk memory addressed one word at a time. Fixed by reading rocket-chip's own `devices/tilelink/TestRAM.scala` (`TLTestRAM`) and adapting its real, proven `TLManagerNode`+`MemoryDevice` pattern directly -- no `regmap` involved at all for the memory itself.
  4. `InModuleBody` used to pre-build the ChipTop IO port threw "InModuleBody contents were requested before module was evaluated" -- rather than debug the exact diplomacy ordering subtlety further, switched to exposing the raw `LazyModule` from the trait and building the actual `IO()` port entirely inside the IOBinder (which is guaranteed to run after full elaboration) -- a simpler, lower-risk pattern.
  5. "No implicit clock" -- a bare `LazyModule` attached only via `pbus.coupleTo` doesn't automatically get implicit clock/reset for its own sequential logic. Fixed by switching to `ClockSinkDomain` + `withClockAndReset(clock, reset) { ... }`, exactly matching how `chipyard.example.GCD`'s own non-externally-clocked case is built.
  6. `val io` declared inside the `withClockAndReset` block became a local value, not accessible as `vga.module.io` from the IOBinder -- moved the `IO()` declaration outside the block, matching GCD's exact structure (IO ports don't need clock context; only the sequential logic driving them does).
- **Software updated to match**: the peripheral ended up as a plain byte-addressable TileLink memory (not the originally-planned per-word register file), which is actually simpler for software -- `DG_DrawFrame` and the new Bad Apple player both write plain packed bytes, MSB-first, matching the existing `.vidf` format's own convention exactly (chosen deliberately so neither DOOM's downsampler nor the Bad Apple player needs any bit-reversal).
- **Bad Apple bare-metal player added**: `badapple_arty100t.c` + `badapple_syscalls.c` (a leaner syscall set than DOOM's -- no WAD file-I/O shim needed, since the `.vidf` is read directly via pointer arithmetic) + `badapple_vidf_embed.S` (`.incbin`, same technique as the WAD embed). Since the `.vidf` format is already exactly 320x200 MSB-first, writing to the new framebuffer is a direct per-row copy, no re-packing needed. Both `doom-arty100t.elf` and `badapple-arty100t.elf` build clean, real, verified ELFs -- built as two separate boot images loaded one at a time via `uart_tsi`, not combined into one image with a menu (matches how bring-up will actually be used).

- **The actual final root cause of "InModuleBody contents were requested before module was evaluated"** (7th attempt, finally traced by reading `InModuleBody`'s own source in `diplomacy/lazymodule/InModuleBody.scala` instead of guessing further): `InModuleBody{}` returns a `ModuleValue[T]`, not `T` -- the conversion to `T` only happens via an implicit conversion applied at first *use*, deferred until after the module is evaluated. An explicit type annotation on the trait's val (`val vga_out: Option[VGAFramebufferOutputBundle] = ...`) forces Scala to apply that conversion **immediately** at trait-construction time, before the module's `execute()` has ever run -- exactly the error. `chipyard.example.GCD`'s analogous `val gcd_busy = InModuleBody { ... }` has no such annotation for precisely this reason. Fix: drop the explicit type, let Scala infer `Option[ModuleValue[...]]`, and let the implicit conversion apply naturally later, in the IOBinder, after the module is real. The `ClockSinkDomain` and `TLInwardClockCrossingHelper` changes made along the way were themselves also real, correct fixes (matching GCD's structure exactly) -- they just weren't sufficient on their own without this one.
- One more small, genuinely final bug after that: `.suggestName("vga")` was used for two different ports (one in the trait's `InModuleBody`, one in the IOBinder) -- "Attempted to name DigitalTop.vga ... with a duplicated name." Renamed one to `vga_periph`.
- **Elaboration succeeded cleanly** for `RocketArty100TVGAConfig`. The framebuffer shows up in the real generated address map at `0x4000000`, matching the address hardcoded in software. Verilog + Vivado TCL generated successfully; real Vivado synthesis is running now via the same Windows bridge used for the earlier clean-timing build.
