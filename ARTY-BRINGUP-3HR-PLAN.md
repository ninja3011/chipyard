## Progress log

- **Vivado invocation confirmed working** via `powershell.exe` interop, non-interactive batch mode.
- **File mirroring done**: `fpga/fpga-shells/` + `fpga/generated-src/<config>/` + one extra vsrc file copied to `C:\arty100t-build\chipyard\...` (~53MB), all absolute Linux paths rewritten to `C:/arty100t-build/chipyard/...` in the 8 affected `.f`/`.json` files.
- **First build attempt failed real**: `ERROR: [Board 49-71] The board_part definition was not found for digilentinc.com:arty-a7-100:part0:1.1`. This Vivado install never had Digilent's board files installed. Fixed by fetching them directly (MIT-licensed, `github.com/Digilent/vivado-boards`, sparse-checkout of just the `arty-a7-100` board files) and adding `set_param board.repoPaths {C:/arty100t-build/board_repo/new}` to a **local, Windows-side-only copy** of `prologue.tcl` (not touching the canonical WSL `fpga-shells` tree).
- **Second attempt**: board part resolved correctly, now generating the MIG DDR3 IP and clock wizard IP — real synthesis setup underway.
- **Real bug caught and fixed in software, independent of the hardware build**: `doomgeneric_arty100t.c` assumed `MTIME_HZ = 1000000` (the common rocket-chip convention); the real generated DTS for this exact config says `timebase-frequency = <50000>` — a 20x error that would have made every `DG_SleepMs`/`DG_GetTicksMs` call badly wrong on real hardware. Fixed, confirmed the UART's separate 50MHz `pbus_clock` was NOT affected (different clock domain, was already correct).
- **Second real bug caught and fixed**: the WAD file-I/O shim's `path_is_wad()` matched any `*.wad` filename, but DOOM's `D_FindWADByName()` tries `doom2.wad` before `freedoom1.wad` in its search order — meaning the shim would have told DOOM `doom2.wad` exists, causing it to latch onto the wrong game mode (commercial/Doom II) while actually reading Freedoom Phase 1 bytes through the shim. Fixed to match only the real embedded filename; verified with a standalone 19-case host-side unit test covering every name in `d_iwad.c`'s candidate list plus adversarial cases (path prefixes, case, near-miss names).
- Hardened `main()` to pass a safe non-NULL fake `argv` rather than trusting whatever bare-metal newlib's `crt0` hands it (defensive, zero-risk).
- Wrote `bringup.sh`, a ready-to-run script for tomorrow: checks for the `uart_tsi` binary and the ELF, runs `+selfcheck` first, then the real boot, with an explicit "what success looks like" checklist so tomorrow is executing against a known checklist, not guessing.
- **Third real bug caught, this one via a genuine dry run, not just re-reading code**: used `socat` to create a virtual serial pair and ran the real `uart_tsi` host tool against the real ELF with no hardware involved, purely to catch host-side loader bugs before spending real hardware transfer time on them. It surfaced that the ELF's LOAD segment actually started at `0x7ffff000` -- one page *below* real DRAM -- because `-Wl,-Ttext=0x80000000` only pins the `.text` section's address, not the whole segment's, and the default linker script places ~4KB of other content before `.text` in the same segment. Fixed with `-Wl,-Ttext-segment=0x80000000`; re-verified both via `readelf -l` (segment now starts exactly at `0x80000000`) and by re-running the same dry run (now loads `80000000-80000400` instead of `7ffff000-7ffff400`).

## Update (autonomous overnight continuation): root-causing and fixing the hold violations

User feedback: timing violations aren't acceptable as a final answer -- chipyard should produce a clean build, and the fix should come from real chipyard behavior/docs, not a guess. Investigated properly:

1. **Checked the official flow itself** (`docs/Prototyping/General.rst`): confirmed `make SUB_PROJECT=arty100t bitstream` is exactly the flow already used tonight -- the manual Windows-side invocation replays the *same* generated `vivado.tcl`/`prologue.tcl`/`route.tcl` etc. verbatim, just launched via `powershell.exe` instead of a `vivado` binary on WSL's `$PATH`. Nothing about the actual FPGA-shells flow was being bypassed.
2. **First hypothesis, checked and disproven**: suspected the JTAG clock's asynchronous relationship to the system clock was undeclared for this harness, since the generic Digilent `arty_a7_100/constraints/arty-master.xdc` template's `set_clock_groups` block references stale port/cell names (`jd_2`, `ip_mmcm`) that don't exist in `Arty100THarness` -- confirmed via real Vivado warnings (`No ports matched 'jd_2'`). This looked like exactly the kind of missing-constraint bug that would explain hold violations.
   - **But**: checking chipyard's own *generated*, per-design `chipyard.fpga.arty100t.Arty100THarness.RocketArty100TConfig.shell.sdc` (the file that actually defines the real, active `JTCK` clock used in the timing report) showed it **already correctly declares `JTCK` as its own separate `set_clock_groups -asynchronous` group**, entirely independent of the stale/dead Digilent template. Chipyard was already doing this correctly. Editing the generic template based on the disproven hypothesis would have been exactly the kind of unfounded "fix" to avoid -- confirmed via real generated output, not left as a guess.
3. **Real root cause, confirmed from the actual failing paths**: all 3 hold violations are same-clock-domain (`clk_out1_harnessSysPLLNode` to itself), inside the RISC-V debug module's program buffer memory -- a physical routing/skew gap left over after `route.tcl`'s generic `phys_opt_design -directive Explore` pass, not a missing constraint.
4. **The fix**: `fpga/fpga-shells/xilinx/common/tcl/route.tcl` now checks hold slack after the existing routing/phys-opt steps, and if (and only if) a hold violation remains, runs an additional `phys_opt_design -directive ExploreWithAggressiveHoldFix` pass -- a real, documented Vivado directive purpose-built for exactly this (UG906's guidance on chaining `phys_opt_design` directives to close whichever violation type remains after a general pass). Verified the directive name is real and accepted by this exact Vivado install (not assumed) via a standalone Tcl check before touching the actual build. The fix is conditional, so clean builds on other boards/configs pay no extra cost.
5. Propagated the fix to the Windows-side build mirror and re-ran the complete official flow from scratch.
